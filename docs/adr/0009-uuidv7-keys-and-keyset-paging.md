# ADR 0009: UUIDv7 keys and keyset paging

Status: accepted

## Context

Submissions are listed newest first, and a form can collect hundreds of thousands of them. Offset paging
(`OFFSET 50000 LIMIT 50`) gets slower with every page. It can also skip or repeat rows when new submissions
arrive between two requests. Random UUIDv4 keys also fragment B-tree indexes, because inserts land everywhere.

## Decision

- All keys are generated by the application with `Guid.CreateVersion7()` (.NET 9 and later). A UUIDv7 starts
  with a millisecond timestamp, so keys are roughly ordered by creation time.
- Submission lists are ordered by `id DESC`. The cursor is the last `id` of a page (`?after=`), and the next page
  is `WHERE id < @after`. The index `(form_id, id)` serves this query directly.
- The response contains `nextCursor`, which is `null` on the last page.

## Consequences

- Every page costs the same, however deep the client pages, and concurrent inserts do not shift pages.
- Index locality is better than with UUIDv4, and keys can still be generated without a database round trip.
- Submissions created in the same millisecond are ordered by the random part of the key. That order is stable,
  but it is not exact to the microsecond. `submitted_at` holds the exact time.
- Clients cannot jump to page *n*. For forms data, "load more" and filters are the usual navigation.

## Alternatives considered

- **Offset paging.** It is simple, but slow at depth and inconsistent under concurrent writes.
- **Database sequences (`bigint identity`).** They are ordered, but they reveal volumes and need a round trip
  before the id is known.
